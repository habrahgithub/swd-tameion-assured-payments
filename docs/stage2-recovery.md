# Stage 2: source review and advisory assessment

Stage 2 records source facts, advisory assessment and explicit human review. It does not authorize a payment, verify a wallet, prove service delivery or activate a controlled instruction. Financial authorization and execution retain their separate gates.

## Current actions and authority

Use the actions returned by the authenticated server. The source adapter evaluates actor status, permission, authority version and window, session/operator/credential and source-ingress binding again after awaits and before protected effects. An expired or changed actor cannot create a new review or dispatch advice. New review expiry is capped by the actor and ingress windows. Half-open expiry means the action is unavailable at the expiry instant.

The recorded HUMAN actor must still have the same active role/version/permission and valid window, and the decision must match the current source/version/policy. A stale or revoked review remains immutable history but is not current authority and cannot prepare a linked draft. Replacing a still-observed review requires its explicit expected_review_hash; the UI carries the server-observed superseded hash. Exact-key historical receipt recovery grants no current approval.

Projection and fresh ordinary AI commands share the same assessment admission rule. Any unresolved assessment at any aggregate/source version blocks a new ordinary V4 AI key. Correcting facts does not erase UNKNOWN, create a successor or renew a dispatch budget. Existing same-key receipt/status/sealing paths retain their access checks and shared-engine behavior without another provider call. Another payable's key cannot be rebound. Explicit legacy disposition/recovery handlers are unchanged; there is no automatic V4 bridge.

An unreadable activated child remains a financial claim. Its independent reconciliation takes priority over source review or historical advice. Current HUMAN review may supersede historical AI guidance, but cannot clear uncertain financial movement, an existing payment lock or mandatory unresolved source findings. Manual review is offered only through current server capability. A contextual manual-review action focuses the existing panel; it grants no extra permission.

## What the messages establish

| Status or category | Known evidence | Owner and permitted next action |
| --- | --- | --- |
| Submitting assessment request | Browser initiated a command; submission/result not confirmed | Wait; retain the original request identity if acknowledgment is lost |
| Request saved / RESERVED / IN_PROGRESS | Durable server reservation, not provider receipt or completion | Check original status; do not create a fresh request |
| UNKNOWN / transport uncertainty | Completion unconfirmed; HTTP/transport failure does not prove no processing | Workspace owner reviews original request; no automatic resend |
| Source changed | Earlier evidence does not establish a current-source result | Finance reviewer checks correction and original history; manual review if allowed |
| Financial history | Existing financial claim remains authoritative | Treasury reconciles the original payment identity |
| Grace period | Server has not yet admitted recovery | Wait and refresh; do not infer successor permission |
| History limit | Prior attempts retained, fresh ordinary AI unavailable | Owner reviews history; current manual capability remains independent |
| Current authority unavailable | Actor/session/ingress binding or window fails | Owner verifies authority, then reload current capabilities |
| Workflow capability unavailable | Required recovery capability not confirmed | Deployment owner verifies admitted migration/capability evidence; hosted cause unverified |
| CONFIGURATION_REJECTED | Committed provider category only | AI Operations verifies approved configuration evidence; manual review if permitted |
| RATE_LIMITED | Committed rate-limit category, not proof of no dispatch | AI Operations reviews limits and original status |
| REFUSED | Provider did not supply usable advice | Finance reviewer reviews actual evidence manually if allowed |
| INVALID_OUTPUT | Returned advice failed validation | Preserve result; review evidence manually |
| Results available | Bound assessment receipt/results available, advisory only | Review findings and current source; human authorization remains separate |

Provider metadata is exposed only from the matching committed sealed assessment record/receipt and source/version. Missing, stale or unrecognized metadata does not establish a provider category. Configuration outcomes may combine upstream HTTP400/401/403/404/422; the application response status is not the provider HTTP status. No message identifies a particular secret, exact upstream401/403 or unique configuration cause without evidence. Technical details show safe category/support codes, never private request keys, raw provider payloads, credentials or exception text.

The synchronous API has no independent safe provider-acceptance signal. Reservation alone never becomes “provider received” or “data sent.” A lost acknowledgment retains the exact session/payable-bound command body/key across reload; changed selection/session and stale responses cannot transfer authority. A pending advisory can recover its original key under the server's observation capability, not fresh-attempt permission. Malformed or unavailable browser storage grants no authority.

## Exact verification limits

Fresh authority and linked-claim observations are checked at application effect boundaries. CAS and existing SQL guards retain durable concurrency/immutable-anchor enforcement. Actor time/status checks immediately preceding dispatch/CAS do not claim an atomic wall-clock/database transaction: a concurrent change after the last observation remains a between-check-and-effect limit. Session validation precedes the last parent authority read; linked children are conservatively rechecked, and a changed parent receipt set refuses mutation. No schema, shared assessment engine, provider, auth or financial policy was changed.

The original SQL-permissive anchor mock is a withdrawn diagnostic, not an acceptance oracle. The faithful SQL-predicate control is an offline simulation, not executed PostgreSQL or evidence of the hosted guard. UNKNOWN plus V4 capability/current-HUMAN UI joins are conditional synthetic composition tests, not a demonstrated hosted payload or screenshot cause.

Verification uses installed pinned Node24.21.0/npm11.19.0 and local synthetic providers, cleared environment and network isolation. The approved tracked public .env.example contains only empty assignments; runtime environment/private source packets are excluded. No real AI, wallet, provider, DB, payment, login or hosted/browser probe is implied by local tests/build. Original operational A2/R3 UNKNOWN and earlier caller correction budgets are unchanged. Production activation, current hosted ingress/capabilities, owner login/session durability and migration readiness remain UNVERIFIED; no publication follows this checkpoint automatically.

Stage2 visible headlines use “Assessment completion not confirmed,” “Submitting assessment request; confirmation pending,” or “Assessment request saved; result pending” according to available evidence. Queue/selected/current controls show the reason and permitted next action nearby; technical details retain the safe original codes. The display-only translator does not change cached legacy labels or known.status identity comparisons. Financial/payment UNKNOWN and reconciliation wording are unchanged. An unrecognized HTTP202 body does not establish a confirmed reservation.

A source-panel advisory response can acknowledge the retained command only with HTTP200 and a canonical receipt for ASM-original-request-key, the selected payable and aggregate version. The caller also compares its original source record/revision with the live source after awaiting the response, and checks the current selection/session and pending command before any category display or key release. The current wire receipt has no independent source hash field; the caller does not invent one. It compares the available live record/revision and version, relying on the authenticated server for committed source binding.

A202 never supplies a committed provider category. The source-panel caller has no canonical key/source/version-bound reservation receipt validator; IN_PROGRESS/RECOVERY_PENDING strings alone do not establish a durable saved request. It keeps all HTTP202 replies unconfirmed and retains the original key. Server read-model reservation facts remain a separate evidence source. Missing, malformed, foreign, wrong-key or stale receipts retain the original command body/key/storage and show unconfirmed completion. A changed selection/session or an unmounted panel drops the late reply; it cannot erase a newer pending command. An exact valid receipt recovered under current server capability still completes the original command without another provider dispatch. These are offline response-boundary guarantees, not evidence of malformed hosted responses or actual financial duplicates.
